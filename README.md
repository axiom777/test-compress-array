## Задание
Есть множество (массив, где порядок не важен) целых чисел в диапазоне от 1 до 300. Количество чисел - от 5 до 1000. Простейший алгоритм сериализует множество в строку вида "1,300,237,188". Напишите функцию сериализации / десериализации в строку, чтобы итоговая строка была компактной (итоговая строка должна быть в 2 раза короче простейшей сериализации для любых возможных наборов чисел).
Цель задачи - максимально сжать данные относительно простой сериализации без алгоритма сжатия.

Сериализованная строка должна содержать только ASCII символы. Можно использовать любой язык программирования.

Вместе с решением нужно прислать набор тестов - исходная строка, сжатая строка, коэффициент сжатия.

## Примеры тестов: 
простейшие короткие, случайные - 50 чисел, 100 чисел, 500 чисел, 1000 чисел, граничные - все числа 1 знака, все числа из 2-х знаков, все числа из 3-х знаков, каждого числа по 3 - всего чисел 900.

## Выбранный стэк
 - JS/TS - так как вакансия на JS

## Размышления
По первоначальным условиям - порядок не важен, значит я могу отсортировать от меньшего к большему.

Есть диапазон в котором может быть 299 вариантов значения, Можно перевести каждое число в ASCII, Стандартный ASCII ограничен 128 кодами, из которых печатными являются только 94, что меньше диапазона чисел (300), поэтому прямая замена числа на символ невозможна.

Была также идея, сделать маркеры для паттернов повторений, но тогда условие, на малых числах не сработает, да и во многих случая строка будет длинее первоначальной, когда паттерны отсутствуют например - [ 7,45,120,200,255 ]

На что я могу влиять, чтобы сжать в 2-х раза - могу убрать запятые, может быть для этого и сделано ограничение, что минимум 5 чисел могут быть на вход 1,2,3,4,5 (9 знаков) 12345 (5 знков), опять же сжатие в 2-а раза не получится - да и число восстановить не смогу.

Что можно сказать - для сжатия, у нас есть в массиве избыточность в запятых и избыточность в порядке, где каждый из них по отдельности не даёт сжатия x2.

Я могу представить набор этих чисел как одно большое число, с учётом того, что есть ограничение на длину массива, значит количество вариантов ограничено и я нагуглил **комбинаторное кодирование** - которое я могу потом перевести в строковое кодирование.

## Комбинаторное кодирование
Суть метода заключается в отображении любого отсортированного набора из чисел (в диапазоне) на его лексикографический порядковый номер (индекс).

Математическая модель: Поскольку числа в наборе могут повторяться, задачу можно рассматривать как `сочетания с повторениями`, а для упрощения вычислений набор приводится к строго возрастающей последовательности , что позволяет использовать формулу сочетаний.

*Эффективность*: Для набора из 1000 чисел в диапазоне 300 количество возможных комбинаций огромно, но конечно. Оно описывается числом, занимающим примерно 450–550 бит. В то время как простая запись строкой занимает до 4000 байт (32000 бит).

*Реализация*: Из-за огромного размера индекса расчеты производятся с помощью арифметики произвольной точности (BigInt в JS).

Первые варианты рализаци комбинаторного кодирования - всё равно не дают сжатие в 2 раза на любых вариантах (коротких). 

Смотрим задачу, что по ней минимальное значение может быть 1,1,1,1,1 - поэтому можно сдвинуть на эту комбинацию и она уместится в 1 символ.

## Строковое кодирование
 - ASCII имеет 94 печатных символа (коды 33–126).
 - Base64 - использует только 64 из них

Разрешается использовать все символы из ASCII, но 0–31 и 127 являются управляющими - они мимо, однако я могу расшириться до Base94, всё таки тоже применяется - это плюс 32% доступного пространства, так как:
 - Символ Base64 несет 6 бит информации.
 - Символ Base94 несет 6.55 бит информации.

### Почему используется именно Base94 (символы ASCII с 33 по 126).
Безопасность: Исключены управляющие символы (0–31, 127) и пробел (32), чтобы избежать проблем при передаче данных через протоколы (HTTP/JSON) и случайного обрезания строки (trimming).

Плотность: Это максимально возможная плотность упаковки для печатаемого ASCII-формата. Каждый символ строки несет бит информации, что на 9.2% эффективнее стандартного Base64.
